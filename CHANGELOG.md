# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- Window style is drawn by the nested Wayland backend: rounded corners (a GLES texture shader that replaces the default for the window's own draw calls), a border (a ring drawn by a pixel shader) and opacity. `Change::Move` animates over the style's transition (`Curve` and duration): the client gets its final size at once and is drawn scaled between the old and the new rectangle, and a move that starts while another is going begins from where the window is drawn.
- Manage hook: `Engine::with_manage_hook`, `Effect::ManageRequested`, `Event::ManageDecided`, `ManageDecision` (move to a workspace, float or tile, focus) and `Engine::pending_manage_requests`. The window is placed by the rules at once and the decision moves it afterwards; the engine never waits.
- External layout: `Layout::External`, `Effect::LayoutRequested`, `Event::LayoutProvided`, `Action::ToggleExternalLayout` and `Engine::pending_layout_requests`. A workspace with it asks for the rectangles of its tiled windows and shows the default layout until an answer that names each window once and stays inside the area arrives; a stale, wrong or missing answer costs only the look of that workspace, and the engine never waits.
- `Event::ActionRequested(Action)`: the engine runs an action asked for by something other than a key (a control tool or a plugin) exactly as it runs a bound key, so the request is an event and a recorded session replays it.
- `Style` (corner radius, border, opacity, `Transition` with a `Curve` and a duration in milliseconds), `Scene::with_style` and `Scene::style_of`, `Change::Style` and `Event::StyleChanged`; the diff announces a style change before the move it animates, and `Error::StyleWindowMissing` rejects a style for a window the scene does not show
- Cargo workspace with three crates: `lutece` (core), `lutece-x11` and `lutece-wayland`
- Core contracts in `lutece::shared::contracts`: `Event`, `Effect`, `Scene` and `Change`
- `diff`, which compares two scenes and returns the minimal changes a backend must apply
- Validated building blocks: non-zero `Size`, `Rect`, `WinId`, `OutputId`, `Modifiers`, `SpawnCommand`
- Optional `serde` feature that serializes the contract types
- Property tests for geometry, ids, modifiers and `diff`, and a Criterion benchmark for `diff`
- `scripts/check` (format, clippy, tests)
- ROADMAP.md, DIARY.md and this changelog
- `StackSet`: workspaces with a current one, each holding its windows as a focus-tracking zipper
- Window operations on `StackSet`: insert, remove, focus next/previous, swap next/previous, focus a window on any workspace
- Workspace operations on `StackSet`: switch by tag or by next/previous with wrap-around, send the focused window to another workspace
- `Tag`, a workspace name that cannot be empty, and the errors `EmptyTag`, `DuplicateTag`, `NoWorkspaces`, `UnknownTag`, `UnknownWindow`
- Model-based property test that runs random operation sequences and checks every window is on exactly one workspace and focus is always valid
- `Layout` enum with `Tile` and `Monocle`, and `Layout::arrange`, which turns a window list and an output rectangle into placements
- `MasterRatio`, the master column's share of the width in whole thousandths (1 to 999), so both columns always keep a pixel
- Tile splits the right column evenly and gives leftover pixels to the first rows, so the rectangles cover the area exactly; monocle puts the focused window on top
- Errors `InvalidRatio`, `AreaTooSmall` and `AreaOutOfRange`
- Property tests for exact coverage, no overlap, window order, and no panic near the coordinate limit
- `Engine`: `handle` applies a backend `Event` to the workspaces and screen and returns the `Effect`s to carry out; `scene` derives the `Scene` to show from the current state
- Events that no longer apply (a close or focus request for an unknown window, a duplicate open) are ignored; key presses do nothing until key bindings exist
- Event-replay integration tests and a property test over random event streams, checking every open window is on exactly one workspace and the scene matches the current workspace
- `lutece-x11`: `X11Backend` connects to the display, becomes its window manager and reports the screen as `OutputsChanged`
- X events translated to `Event`: map requests become `WindowOpened` (with title, class and transient parent), client unmaps and destroys become `WindowClosed`, and the pointer entering a window becomes `FocusRequested`
- `X11Backend::apply_scene` shows a `Scene` by applying only the `diff` from what is shown (place, map, unmap, restack, focus); `apply_effects` closes windows politely, spawns programs and reports `Flow::Quit`
- The caller owns the loop: `next_events` blocks, `pending_events` does not, and `AsFd` lets other inputs share a `poll`
- Error type for the backend, including `AnotherWindowManager` when the display already has one
- Property tests for event translation and for scene application against a fake server
- Dependencies for `lutece-x11`: `x11rb`, `thiserror` (and `proptest` for tests)
- `minimal` example (`cargo run -p lutece-x11 --example minimal`): a window manager in one file that tiles every window on a single workspace; stop it with Ctrl-C or by closing the nested X server
- `scripts/dev-x11 [display]`: builds the `minimal` example, starts Xephyr on a spare display (default `:2`, size from `LUTECE_SCREEN`), waits for it, runs the window manager in it and stops Xephyr on exit
- Key bindings: `Keymap` (key combination to `Action`, one action per combination) and the `Action` enum (quit, close, spawn, focus and swap next/previous, view a tag, move to a tag)
- `Engine::with_keymap` and `Engine::grabs`; a `KeyPressed` event now runs the bound action and returns `Quit`, `Close` and `Spawn` as effects
- `Keysym::RETURN` and `Keysym::from_char`, and the error `DuplicateBinding`
- `X11Backend::grab_keys` grabs key combinations on the root window, also with CapsLock and NumLock held, and key presses reach the core as `KeyPressed`; errors `UnmappedKeysym` and `KeyAlreadyGrabbed`
- Property tests for the keymap, the keycode lookup and the modifier conversion, and replay tests for every key action
- `X11Backend::connect` adopts windows already on screen: each showing, non-override-redirect window is reported as `WindowOpened` after the screen, bottom of the stack first
- Tests that only showing client windows are adopted, once, and that an adopted window is hidden with a real unmap

- Layout keys: the `Action` variants `NextLayout`, `GrowMaster` and `ShrinkMaster`; growing and shrinking move the master column by 5% and are ignored by layouts without one
- `Workspace::layout`, `StackSet::next_layout` and `StackSet::resize_master`, and `MasterRatio::step`, which moves a ratio and stops at the 1 to 999 limits
- Tests for `MasterRatio::step`, for tile getting its ratio back after a trip through monocle, and for replaying the layout keys through the engine
- The `minimal` example binds Super+space (next layout) and Super+h / Super+l (narrow / widen the master column)
- Manage rules in `lutece::rules`: `Rules` is an ordered list of `ManageRule`s, each a `Match` (class, title or dialog) and an `Outcome` (`Ignore` or `SendTo(Tag)`); the first match decides
- `Engine::with_rules`, which refuses rules that send windows to a workspace the engine lacks; `StackSet::insert_on` adds a window to a given workspace without switching to it
- `Effect::Release`: the core stops managing a window and leaves it to its client; the X11 backend maps it, forgets it and answers its configure requests as it asks
- Tests for rule matching and order, for send and ignore rules replayed through the engine, and for a released window never being reported again
- The `minimal` example ignores `Xmessage` windows and opens `Firefox` on workspace 9
- Floating windows: a floating window is left out of the layout and drawn above the tiled ones, in the scene `Engine::scene` builds
- `Outcome::Float`, which opens a matching window floating on the current workspace
- Actions `ToggleFloat`, `MoveFloat(Direction)` and `ResizeFloat(Direction)`, and the `Direction` type; a step is 40 pixels and the smallest size is 64 pixels
- `Workspace::is_floating` and `StackSet::toggle_float`; a window keeps floating, and its place, when it moves to another workspace
- Tests for the float arithmetic (valid rectangle for any input, undoable moves, no dead zone at the size floor), for float state on workspaces, and for float rules and keys replayed through the engine
- The `minimal` example floats dialogs and binds Super+f (toggle), Super+Ctrl+h/j/k/l (move) and Super+Ctrl+Shift+h/j/k/l (resize)
- Keyboard remapping: the X11 backend refetches the keycode table on a keyboard `MappingNotify` and grabs its keys again, so bindings follow their keys after a layout change; keys the new layout lacks are skipped
- Integration tests in `crates/lutece-x11/tests/integration` that run the `minimal` example on a private `Xvfb` and press keys through XTEST (tiling, rules, floating, layout keys, workspaces, close, quit, keyboard remap)
- `scripts/ci`, which runs `scripts/check` and fails if `Xvfb` is missing, and a GitHub Actions workflow that calls it
- `Layout::Grid` (rows of equal height, as square as the count allows) and `Layout::CenteredMaster` (the master in a middle column, the rest alternating to its right and left); both cover the area exactly, checked by property tests
- `GrowMaster` and `ShrinkMaster` also move the centered master's column
- Multi-output support: `StackSet` shows its workspaces on screens, one per output, with the rest hidden; `StackSet::set_outputs`, `screens`, `current_output`, `focus_next_output`, `focus_prev_output`, `send_focused_to_next_output` and `send_focused_to_prev_output`
- Actions `FocusNextOutput`, `FocusPrevOutput`, `SendToNextOutput` and `SendToPrevOutput`
- Unplugging an output hides its workspace with its windows; a new output takes the workspace of one that vanished, then the first hidden one; outputs past the number of workspaces get no screen
- The X11 backend lists monitors with RandR 1.5 (the `randr` feature of `x11rb`), reports a new set of outputs when they change, and falls back to the whole root window as one output without RandR 1.5
- Tests: a model-based property test over screen changes and output keys, unit tests for `set_outputs`, engine replays with two outputs (including a generated stream with changing outputs), and `monitors` integration tests that need `Xvfb`
- The `minimal` example binds Super+, / Super+. (focus the previous / next monitor) and Super+Shift+, / Super+Shift+. (send the focused window there)
- `lutece-wayland`: `WaylandBackend`, a Smithay compositor the caller drives like `X11Backend`; it serves clients on a free `lutece-N` socket, reports xdg toplevels as `WindowOpened` on their first commit (and `WindowClosed` when destroyed), reports a virtual output as `OutputsChanged`, and answers the core with `apply_scene` and `apply_effects`
- `WaylandBackend` tells each client the size its placement gives it, marks the focused window active and gives it the keyboard, closes windows on `Effect::Close`, and starts programs with `WAYLAND_DISPLAY` set to its own socket; `Effect::Release` leaves the window unplaced because Wayland has no client to hand it back to
- `WaylandBackend::key_event` and `KeyAction`: key combinations from `grab_keys` are returned to the caller and hidden from clients, their release included; Caps Lock and Num Lock do not change a match
- `lutece-wayland`: `NestedBackend` shows the compositor in a window of the running session through Smithay's winit backend, follows the window's size, draws the placed windows and answers their frame callbacks
- `lutece-wayland` example `minimal`: a keyboard-driven tiling WM on `NestedBackend`, bound to Alt so the session around it keeps Super
- Tests: integration tests in which a real Wayland client is stepped in turn with the backend (output report, first-commit announcement, sizes from the scene, focus and activation, destroy, close, grabbed keys), and a property test for modifier translation
- `Event::FloatAdjusted`: a pointer drag of a floating window, as pixel movement and growth; the engine applies it with the same float logic as the move and resize keys and ignores it for tiled or unknown windows
- `lutece-wayland`: the pointer. `WaylandBackend::pointer_motion`, `pointer_button` and `pointer_axis` feed pointer input; entering a window reports `Event::FocusRequested`, clients receive motion, buttons and wheel, and with the drag modifier held (`set_drag_modifier`, Alt by default) the left button starts a move and the right button a resize, reported as `Event::FloatAdjusted` and hidden from clients
- `lutece-wayland`: popups are configured where their client asks, drawn above their window, found under the pointer, and dismissed by a click outside when they grabbed the pointer
- `lutece-wayland`: copy and paste between clients through the clipboard (data device) and the primary selection, which follow keyboard focus
- `NestedBackend` takes pointer input from its window, shows the cursor a client asks for (a named cursor in the window, a client-drawn one with the windows) and has `set_drag_modifier`
- Tests: core tests for `FloatAdjusted` including a property test that dragging and dragging back restores the scene, and Wayland integration tests for hover focus, buttons and wheel, move and resize drags, sub-pixel drags, popup placement, popup hit-testing and dismissal, and a clipboard transfer between two clients
- `lutece-x11`: pointer drags. `X11Backend::set_drag_modifier` grabs the left and right buttons with the modifier held; the left button moves and the right button resizes the window under the pointer, reported as `Event::FloatAdjusted` and hidden from its client. The new error `DragAlreadyGrabbed` reports a combination another client holds. The `minimal` example uses Super
- `lutece-wayland`: `xdg-decoration`. Every toplevel is told the compositor decorates it, whatever it asks for, and the compositor draws no frames, so clients drop their own title bars
- `lutece-wayland`: a window is placed by the window geometry its client declares, so the part inside a shadow or margin lines up with its place, and the pointer finds the surface at the right spot
- `lutece-wayland`: popups stay on the output. The positioner's slide, flip and resize rules are applied against the output holding the parent window when a popup opens and when it is repositioned, also for a popup opened from a popup
- `lutece-wayland`: several outputs. `WaylandBackend::set_outputs` takes the complete set; a new id gets a `wl_output` global, a missing id loses it and a kept id takes its new area. The core hears a pending set only once, as the latest
- `NestedBackend::open_with_outputs` cuts the window into outputs of equal width side by side; they follow the window when it is resized. The example reads `LUTECE_OUTPUTS` and binds Alt+, Alt+. and their Shift variants for moving between outputs
- Tests: a property test that dragged steps add up to the pointer's displacement, a property test that the nested outputs tile the window, a property test for the popup target, and Wayland integration tests for decoration negotiation, geometry offsets, a popup sliding back onto the output and outputs added, moved and removed
- `Scale` and `WaylandBackend::set_scale`: the Wayland backend can tell clients how many physical pixels a logical pixel is; it offers `wp_fractional_scale` and `wp_viewporter`, and an output announces the scale rounded up and the physical mode that covers its logical area
- `NestedBackend` follows the scale factor of the host window, and its changes, and measures outputs and the pointer in logical pixels
- The Wayland backend cuts each window's surface to the rectangle the core gave the window, so a client's shadow or frame does not paint over a neighbouring window
- Property tests for the scale (a length survives a trip to physical and back at any scale of 1 or more; touching rectangles still touch) and protocol tests with a real client for the scale, the output and the viewport
- Wayland output enter: a window's surfaces and its popups get `wl_surface.enter` and `leave` for the outputs the window's rectangle overlaps, and `preferred_buffer_scale` with the host scale rounded up, so clients without `wp_fractional_scale` draw sharp; refreshed on place, hide, move, output changes and scale changes
- Wayland `linux-dmabuf` (version 4 with default feedback): `WaylandBackend::enable_dmabuf` and `DmabufSupport` describe the render GPU and its formats, and `NestedBackend` fills them in from its EGL device, so GPU clients share buffers without copying
- Integration tests for the new behaviour with a real client (output enters at the seam, on move, hide, unplug and output growth; buffer scale; popups; the dmabuf global, its feedback and buffer creation), and property tests for the overlap rule
- `lutece-wayland`: X11 programs through Xwayland. `WaylandBackend::enable_xwayland` starts Xwayland and the window manager side it needs (and `NestedBackend::enable_xwayland`), `xwayland_display` says when it is ready, and a spawn effect then sets `DISPLAY` for the program. An X11 window is reported as `Event::WindowOpened` with its title, class and parent dialog, and is tiled, floated, focused and closed like a Wayland one; the X input focus follows the core's focus. X11 menus and tooltips are drawn above all windows where their program put them, take the pointer, and are never managed. A failed start is reported once as `Error::XWayland`
- The `minimal_wayland` example turns Xwayland on, prints the `DISPLAY` to use, and keeps running without X11 programs if Xwayland cannot start
- X11 integration tests for mouse drags (Super+left-drag moves, Super+right-drag resizes, a drag without the modifier does nothing) and a pointer-drag helper in the test client
- Wayland integration tests with a real Xwayland and an X11 client: a window is reported with its title and class, placed, shares the screen with a second one, closes, a menu stays unmanaged and in front, and the focused window gets the X input focus; unit tests for how a configure request is granted
- `lutece-wayland`: copy and paste between X11 and Wayland programs, for the clipboard and the primary selection. Only the list of formats crosses when a selection is set; the data is fetched when someone pastes. An X11 program can read a Wayland selection only while an X11 window has the keyboard focus, and a selection held by a Wayland client is not cleared when an X11 program gives up its own
- `lutece-wayland`: an `input` module that turns events from any Smithay input backend into keyboard and pointer input for the compositor, with a relative pointer kept inside the output
- Integration tests for selections crossing between X11 and Wayland clients
- Fullscreen windows in the core: `Event::FullscreenRequested`, `Action::ToggleFullscreen`, `StackSet::toggle_fullscreen` and `Workspace::fullscreen`. A fullscreen window covers its whole output and is drawn above everything on it; only the focused window can be fullscreen, so moving the focus, closing the window or opening another ends it. `Scene::with_fullscreen` and `Scene::is_fullscreen` carry the state, `diff` reports it as `Change::Fullscreen` ahead of the window's move, and `Error::FullscreenWindowMissing` rejects a fullscreen window the scene does not list
- Reserved space in the core: `Event::ReservedChanged`, `Insets` and `Rect::inset`. Bars report what they keep clear of an output, and tiled and floating windows are laid out in what is left; a claim on more than half of an axis is ignored on that axis. Property tests for `Rect::inset`, `Insets::limited_to`, the scene's fullscreen set and the fullscreen invariants of `Workspace`, and the random event stream test now includes both new events
- `lutece-x11`: bars. A window of type dock is mapped where it asks and never managed; its `_NET_WM_STRUT_PARTIAL` or `_NET_WM_STRUT` is worked out per monitor, tracked as it changes and when the bar goes away, and bars already showing at startup are included. Two bars on one edge reserve the larger, not the sum
- `lutece-x11`: `_NET_WM_STATE` fullscreen. Add, remove and toggle requests become `Event::FullscreenRequested`; a window that sets the state before it maps starts fullscreen; the backend writes the property from the scene and clears it when a fullscreen window is hidden. `_NET_SUPPORTED` and `_NET_SUPPORTING_WM_CHECK` tell toolkits what is honoured. `Error::Create` covers a failed resource id
- `lutece-wayland`: `wlr-layer-shell` (version 4). Bars, launchers and wallpapers are placed by the compositor and never tiled; the space they keep clear reaches the core as `ReservedChanged`. Stacking is overlay, fullscreen windows, top, windows, bottom, background. They receive the pointer; a surface with exclusive keyboard interactivity holds the keyboard, one that asks on demand gets it when clicked until the pointer enters a window; popups of a bar are placed where the client asks; surfaces on an output that goes away are asked to close, and a request with no output is closed at once
- `lutece-wayland`: fullscreen. `xdg_toplevel` fullscreen and unfullscreen requests, also before the first commit, and X11 requests through Xwayland become `Event::FullscreenRequested`; the state is sent with the configure that sizes the window and is cleared when the window is hidden
- Fullscreen keys in both examples (Super+Shift+f on X11, Alt+Shift+f on Wayland)
- Integration tests: X11 bars and fullscreen on a private `Xvfb` (a bar leaves the tiles room, one that was showing before the window manager started, closing, resizing, two bars, a claim on most of the screen, a bar over one of two monitors, the request, the toggle, the key, a window that starts fullscreen, a new window ending it, state across a workspace switch); Wayland layer-shell and fullscreen with scripted clients and with a real Xwayland
- X11 backend: a bar that is override-redirect (it maps without asking the window manager) is kept as a bar when it has a strut, also when it sets the strut after it maps or was showing at startup; menus and tooltips have none and are ignored
- `lutece-wayland`: an X11 program that sets `_NET_WM_STATE` fullscreen before it maps is seen asking; the backend reads the property through its own connection to Xwayland and sends `FullscreenRequested` right after `WindowOpened`
- `lutece-wayland`: the stacking order of X11 windows under Xwayland follows the scene (`_NET_CLIENT_LIST_STACKING`), a fullscreen window above the others; it is redone when the order or a fullscreen state changes

### Changed
- `Engine::scene` lays out in the area bars leave free and puts a fullscreen window on the whole output; floating windows are centered in the free area
- `Scene` now holds the set of fullscreen windows; `Scene::try_new` is unchanged and starts with none
- `Change` gains `Fullscreen`; backends that match on it already have a catch-all arm, since the enum is `#[non_exhaustive]`
- `lutece-wayland` draws, hit-tests and answers frame callbacks from one list of layers in front-to-back order, which now includes layer surfaces
- `lutece-wayland` has `wayland-protocols-wlr` as a test dependency
- `lutece-wayland` imports in `dmabuf.rs` and `selection.rs` are sorted the way `cargo fmt` wants them; no code changed
- `Engine::scene` now builds the scene for every screen, each in its own output's area, instead of one workspace on the first output; its focus is the focused screen's focused window
- `StackSet::focus_tag` and `focus_window` give the focus to the screen that already shows the workspace, and otherwise replace the focused screen's workspace; `move_focused_to` and `insert_on` work on any workspace, shown or hidden
- A floating window is placed relative to the area of its own output, and resizing uses the focused output
- `StackSet::new` starts with one screen, for output 0, until `set_outputs` is called
- `NextLayout` now cycles tile, monocle, grid, centered master; tile and centered master share one master ratio per workspace
- Each workspace now holds its own layout instead of the engine holding one for all; `Engine::new` still takes a layout, which every workspace starts with
- `WaylandBackend::set_output_size` is now the one-output form of `set_outputs`: it removes any other output
- The `minimal` example has nine workspaces and key bindings (Super+Return, j/k, 1-9, Shift variants, c, q); it no longer needs to be stopped from outside
- A popup whose window moves is dismissed when its positioner rules would now put it elsewhere (a menu slid back from an edge, or one that would leave the output); other popups follow their window
- The Wayland compositor global is now version 6, which is what lets a surface be told its preferred buffer scale
- `lutece-wayland` enables Smithay's `backend_drm` feature (the `drm` crates) to identify the render node for dmabuf feedback
- The `lutece-wayland` example is now named `minimal_wayland` (it was `minimal`, like the X11 example, and building one overwrote the other's binary in `target/<profile>/examples`); run it with `cargo run -p lutece-wayland --example minimal_wayland`
- `lutece-wayland` enables Smithay's `xwayland` feature and has `x11rb` as a test dependency
- `lutece-wayland`: input handling moved out of `NestedBackend` into the `input` module; `linux-dmabuf` feedback is built from the renderer's own GPU; the compositor state keeps the event loop handle that selection transfers need; Smithay is built with the DRM, GBM, udev, libinput, libseat and multi-GPU features, ahead of a session backend
- `lutece-wayland` gives each Xwayland instance a display number from a process-wide counter instead of Smithay's lowest free one (the first is still the lowest free); `x11rb` 0.14 moves from the dev-dependencies to the dependencies

### Fixed
- The nested Wayland window drew everything upside down (found the first time it was looked at, with a bar and three terminals in it): the winit framebuffer has its origin at the bottom, so the frame is now drawn with `Transform::Flipped180`.
- `lutece-wayland`: `_NET_ACTIVE_WINDOW` under Xwayland named the root or the window that had just lost the focus; it now names the X11 window that has the keyboard focus, and none when a Wayland surface has it
- The X11 integration tests failed at random (about half of the runs) with `Connection reset by peer`: the private `Xvfb` restarted when the readiness probe closed the only connection it had, and the test client's own connection landed in the restart. The server now starts with `-noreset`
- The X11 integration tests started the Wayland example instead of the X11 one after both had been built, and then every test timed out waiting for the window manager
- The X11 test helper that swaps two keys copied the first key's symbols over the second's, so the keyboard remap test could not find the key it had just remapped
- The Xwayland integration tests failed in about 1 run in 8 with `Connection refused`: a display number released by one Xwayland instance was taken at once by the next, and the older instance deleted the lock and socket files of the newer one. No failure in 100 runs after the change
